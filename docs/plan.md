# План: настольное приложение «Канбан»

Документ фиксирует, что именно делаем и почему — от исследования метода до проверок готового продукта.

## 1. Что такое канбан (кратко, из исследования)

**Происхождение.** Слово «канбан» — японское: 看 (kan) «видимый, сигнал» + 板 (ban) «доска, карточка». Метод родился на заводах Toyota в 1940–50-х: Тайити Оно предложил pull-систему — производить только то, на что есть реальный запрос. Карточки стали сигналом: «нет карточки — нет задачи».

**Адаптация для знаний.** В 2004-м Дэвид Дж. Андерсон применил производственную логику к ИТ-команде в Microsoft: скорость завершения задач выросла более чем в 3 раза, время выполнения упало на ~90%, своевременная поставка поднялась с 0% до 98% за 15 месяцев. В 2010-м вышла его книга «Kanban: Successful Evolutionary Change for Your Technology Business» — базовое пособие метода.

**Четыре принципа.** Визуализируй работу → ограничивай незавершённое (WIP) → управляй потоком → улучшайся непрерывно.

**Практики, из которых выросли требования к приложению:**

| Практика | Что даёт | Отражение в приложении |
|---|---|---|
| Визуализация потока | работа видна целиком, статусы обновляются по факту | доска с колонками-этапами и стикерами |
| WIP-лимиты | не брать больше, чем можно завершить; меньше переключений | предел задач на колонку; вход сверх лимита отклоняется |
| Pull-система | новую работу берут, когда освободился ресурс | счётчик `3/3`, краснеет на пределе |
| Явные правила | понятно, что значит «готово» | колонка «Завершено» с приглушённым видом, метка «готово» |
| Управление потоком | блокеры и ожидания видны | колонка «На ожидании», флаг «срочно», крайние сроки |
| Метрики | решения на основе цифр | счётчики по колонкам, подсветка просрочки |

**Типовые ошибки** (из тех же источников): слишком много колонок, отсутствие лимитов, забытые блокеры, «витрина задач» вместо рабочего инструмента. Вывод для дизайна: колонок по умолчанию — пять, лимит «В работе» задан по умолчанию (3), блокеры отражены отдельной колонкой.

## 2. Требования (из постановки владельца)

1. Доска из нескольких вертикальных полей: пул задач, срочные, в работе, на ожидании, завершённые.
2. Задачи — свободно перемещаемые стикеры (перетаскивание мышью куда угодно).
3. Ориентир — лист OneNote, но с собственным оформлением.
4. Плавно, легко, быстро, красиво.
5. Десктоп-приложение, репозиторий на GitHub.

## 3. Решения

- **Electron.** Десктоп-приложение на веб-технологиях: лучший контроль над анимациями и перетаскиванием, кросс-платформенные сборки (Linux/Windows/macOS) из одной кодовой базы. Альтернативы (Tauri — сложнее в контейнере, Qt — тяжелее по вёрстке) отклонены.
- **Без внешних зависимостей в рантайме.** Drag-n-drop, редактор, тосты — своими руками на pointer-событиях. Меньше вес, предсказуемое поведение.
- **Ядро отдельно от UI.** `src/core/store.js` — чистый модуль без DOM; юнит-тесты гоняются в Node, смоук-тест — в настоящем Electron.
- **Локальный JSON + автосохранение.** Файл в каталоге данных приложения; атомарная запись; санитизация при загрузке.
- **Оформление.** Тёплая бумажная палитра, пастельные стикеры с наклонами, рукописные шрифты (Neucha, Caveat — SIL OFL), анимации только transform/opacity.

## 5. Критерии приёмки

- Перетаскивание стикера работает мышью в любую колонку и на любую позицию внутри колонки.
- Перемещение в колонку с достигнутым WIP-лимитом отклоняется с объяснением.
- Ни одно действие не требует «сохранить» руками: всё пишется само.
- Удаление обратимо. Поиск не портит данные.
- Битый файл доски не роняет приложение.
- Юнит-тесты и смоук-тест зелёные; приложение собирается в дистрибутив.

## 6. Фактические результаты проверок

**Юнит-тесты ядра** — `npm test`, 25/25 зелёные. Покрывают: стартовую доску, создание
(в том числе наверх колонки), WIP-лимиты при создании и переносе, вставку между
соседями, начало/конец колонки, невырождение порядка на 40 вставок в одну щель,
правку полей, мягкое удаление и возврат, дублирование, поиск, операции с колонками,
автосохранение и ошибку диска, санитизацию битых данных, вычистку старого архива,
подсчёт просрочки, нормализацию порядков.

**Смоук-тест в реальном Electron** — `npm run smoke`, 26 проверок, все зелёные.
Ключевое: живое перетаскивание симулировано pointer-событиями — призрак появляется,
колонка подсвечивается, слот вставки показывается, стикер переезжает в «Завершено»,
а в переполненную колонку не пускается. Плюс проверки сохранения (файл реально
записан и перечитан) и жизненного цикла колонок.

**Кадры** — `artifacts/preview.png` (доска) и `artifacts/preview-editor.png` (редактор),
сняты из работающего приложения.

**Сборка** — AppImage 1.0.0 собран и проверен: смоук-тест проходит прямо из
упакованного образа (`--appimage-extract-and-run`). Windows-инсталлятор (NSIS)
собирается отдельно под wine.
